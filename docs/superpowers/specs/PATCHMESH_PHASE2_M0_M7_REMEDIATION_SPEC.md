# PatchMesh Phase 2 M0 and M7 Remediation Specification

Status: Proposed implementation specification

Repository baseline: `793b98a510f8dfa287eb2c7c1ef9909287840c30`

Scope: Phase 2 M0 performance gate and M7 production-evidence/quality gate

Authority: Report-only; this work must not add `delay` or `reject`

## 1. Purpose

This specification defines the work required to make the Phase 2 M0 and M7 gates
trustworthy and passable without fabricating evidence, weakening detector semantics,
or declaring Phase 2 complete prematurely.

The implementation must preserve the PatchMesh boundaries:

- adapters observe and translate runtime activity;
- analyzers produce deterministic facts;
- detectors produce findings;
- policies remain report-only;
- storage remains append-only and replayable;
- `.evidence` is a bounded review journal, not the source of truth for effects.

## 2. Current blockers

### 2.1 M0 blockers

1. `tools/phase2/m0-budget-report.ts` hard-codes `30 / 60 / 120 ms`, while the
   checked-in Phase 2 measurement artifact uses provisional budgets of
   `250 / 1500 / 5000 ms` for `1,000 / 10,000 / 50,000` files.
2. The budget definition, benchmark generator, and evaluator do not share one
   versioned workload contract.
3. Only five measured samples and zero warm-up runs are recorded. Nearest-rank p95
   over five samples is merely the maximum and is too sensitive to noise.
4. `NodeObservationBoundary` traverses and hashes the whole workspace at both sides
   of every tool call and repeats Git metadata subprocesses.
5. The repository has no canonical command that generates and verifies M0 evidence
   from a clean, identified revision.

### 2.2 M7 blockers

1. No production host owns a real tool execution path and invokes
   `McpProxy.execute` around that execution.
2. The committed `.evidence` traces contain valid run attribution but no verified,
   completion-linked real effects.
3. `field-corpus.ts` verifies trace and output digests but does not rerun a detector
   from a canonical PatchMesh protocol-event slice.
4. The current detector output is considered bound when it repeats corpus fields,
   including reviewer-owned `expectedFinding`. A hand-authored output can therefore
   satisfy artifact binding.
5. `observedFinding` and `confidence` are supplied by the corpus rather than derived
   from detector output.
6. Twenty holdouts with only five negatives can satisfy the current structural gate,
   but cannot substantiate a 2% false-positive-rate claim.

## 3. Non-negotiable invariants

The following requirements use the RFC 2119 meanings of MUST, MUST NOT, SHOULD, and
MAY.

1. A deterministic tie-break, timestamp, filename, event ID, or arrival order MUST
   NOT be converted into causal or concurrency proof.
2. M0 MUST be evaluated from raw benchmark samples generated by the canonical
   benchmark command. Summary values in an input file MUST be ignored and recomputed.
3. A budget change MUST create a new versioned workload definition and an explicit
   documentation decision. It MUST NOT be hidden in evaluator constants.
4. M7 detector results MUST be reproduced by executing the checked-in detector code
   over validated protocol events.
5. Reviewer labels MUST be stored separately from generated detector output.
6. A runtime post-tool hook that did not own or wrap the executor MUST NOT be described
   as a production host adapter.
7. Requested paths, command text, tool input, tool output, or hook-supplied effects
   MUST NOT become verified effect evidence.
8. Only persisted `file.changed` events linked by the persisted `tool.completed`
   event and sufficient coverage MAY become verified evidence effects.
9. Missing, ambiguous, bypassed, overlapping, or invalid observation MUST fail closed
   as degraded/unavailable. It MUST NOT become either a finding or a verified negative.
10. Raw local agent traces MUST NOT be committed by default. A real case may enter a
    reviewed corpus only after minimization, validation, redaction, and human approval.
11. M0 or M7 acceptance MUST NOT change the report-only authority level.
12. Passing M0 and M7 MUST NOT by itself mark Phase 2 complete; M1-M6 exit evidence
    remains independently required.

## 4. M0 specification: trustworthy observation-performance gate

### 4.1 Canonical workload contract

Add `benchmarks/phase2/m0-workloads.v1.json` as the sole M0 v1 definition:

```json
{
  "schemaVersion": 1,
  "definitionVersion": "phase2-m0-v1",
  "metric": "incremental_interception_overhead_ms",
  "percentile": 0.95,
  "warmupSamples": 5,
  "measuredSamples": 30,
  "independentRuns": 3,
  "workloads": [
    { "workloadId": "small", "fileCount": 1000, "budgetMs": 250 },
    { "workloadId": "medium", "fileCount": 10000, "budgetMs": 1500 },
    { "workloadId": "large", "fileCount": 50000, "budgetMs": 5000 }
  ]
}
```

Rationale: `250 / 1500 / 5000 ms` is the only checked-in full-
`NodeObservationBoundary` provisional budget set on the baseline revision. The
`30 / 60 / 120 ms` evaluator constants have no matching workload definition or
measurement artifact and must be removed. If maintainers intentionally choose a
stricter contract later, they must add `phase2-m0-v2` rather than modifying v1.

The definition MUST also specify or its validator MUST enforce:

- repository fixture generator version;
- file-size distribution and deterministic content seed;
- ignored-path policy version;
- exactly one changed hot file per measured operation;
- no network access;
- temporary local Git repository and SQLite store;
- environment fields: timestamp, commit, dirty flag, OS, OS release, architecture,
  CPU, memory, Node version, pnpm version, and workload-definition digest.

### 4.2 Measurement definition

Each sample MUST be paired:

1. Run the exact executor operation directly and record `baselineNs`.
2. Restore the fixture to the same logical pre-state outside the timed section.
3. Run the same executor once through `McpProxy.execute` using the real
   `NodeObservationBoundary` and record `instrumentedNs`.
4. Compute `overheadNs = max(0, instrumentedNs - baselineNs)`.

The measured executor MUST modify one deterministic file and explicitly report that
resource identity to the adapter. Fixture creation, initial watcher startup, initial
full snapshot, Git initialization, database creation, restoration, and artifact writes
MUST occur outside the timed section.

Cold initialization MUST be measured and recorded in a separate non-gating
`coldInitializationMs` field. Moving initialization out of the per-tool critical path
is allowed; hiding it entirely is not.

For each tier:

- perform 5 warm-up samples;
- perform 30 retained samples per independent run;
- perform 3 independent runs with new temp repositories;
- record every baseline, instrumented, and overhead value;
- record failures per sample;
- compute p50 and nearest-rank p95 from overhead samples in each run;
- compute the gate value as the maximum p95 across the 3 runs.

Replace the manually shaped artifact with a generated report containing at least:

    warmupSamples: number;

The artifact MUST NOT accept supplied `p50Ms`, `p95Ms`, `gateP95Ms`, `failures`,
`accepted`, `decision`, or `reason` as authoritative input. The verifier recomputes all
of them from raw samples and the referenced workload definition.

An accepted artifact MUST have:

- exact tier set: small, medium, large;
- exact file counts and budgets from the versioned definition;
- exact sample/run counts;
- only real `node_observation` samples;
- zero failures;
- finite, non-negative timing values;
- `gitDirty === false`;
- `commit` equal to the revision being accepted;
- matching definition digest;
- every tier's maximum run p95 at or below its budget.

Any violation returns `deferred` with typed diagnostics. Invalid schema, digest, or
sample values return `rejected`; the verifier MUST NOT throw a generic untyped error.

### 4.4 Incremental `NodeObservationBoundary`

The steady-state path MUST be proportional to changed candidate paths rather than all
workspace files.

Implement an internal per-workspace observation session with this lifecycle:

1. Start the filesystem watcher before the initial full scan.
2. Build the initial content-hash state once.
3. Drain and re-observe watcher entries received during initialization so there is no
   scan/watcher gap.
4. At tool start, flush the watcher queue and record a monotonic journal cursor.
5. At tool completion, wait for a bounded quiescence barrier, drain unique candidate
   paths after that cursor, and hash only those paths.
6. Produce before/after state for each candidate and update the cached workspace state.
7. Treat changes observed between tool windows as out-of-band changes.
8. Periodically reconcile with a full scan outside the tool critical path.

Add a window-based observation API while retaining the snapshot API as a compatibility
fallback:

```ts
interface ObservationWindow {
  readonly windowId: string;
  readonly context: ObservationContext;
  readonly startCursor: number;
  readonly repositoryBefore: RepositoryObservation;
  readonly gaps: readonly ObservationGap[];
}

interface ObservationWindowResult {
  readonly changes: readonly ObservedFileChange[];
  readonly outOfBandChanges: readonly ObservedFileChange[];
  readonly repositoryAfter: RepositoryObservation;
  readonly startCursor: number;
  readonly endCursor: number;
  readonly completeness: "complete" | "degraded";
  readonly gaps: readonly ObservationGap[];
}

interface IncrementalObservationBoundary extends ObservationBoundary {
  beginWindow(context: ObservationContext): Promise<ObservationWindow>;
  endWindow(window: ObservationWindow): Promise<ObservationWindowResult>;
}
```

`McpProxy` SHOULD use `beginWindow/endWindow` when available and retain the existing
`captureBefore/captureAfter + diffSnapshots` path for other boundary implementations.
Business logic must not move into the observer.

#### Required failure behavior

- Watcher overflow, recursive-watch unavailability, queue loss, root replacement,
  unbounded symlink behavior, or reconciliation mismatch MUST mark the window
  `degraded` and require a full reconciliation.
- Two overlapping active windows for one workspace MUST NOT both claim deterministic
  attribution. Unless the host proves exclusive execution, affected changes are
  `unattributed` or `degraded`.
- A candidate path that cannot be read or hashed MUST create an explicit gap.
- A deletion MUST be represented without attempting to hash missing content.
- A rename MUST be represented only when deterministically paired; otherwise emit a
  delete plus create.
- Ignore rules MUST be versioned and shared by initialization, watcher, reconciliation,
  and benchmark fixture validation.
- `.git`, `.evidence/runtime`, dependency trees, and generated output MAY be ignored
  only through that explicit policy; ignored paths are coverage scope, not observed
  safety.

#### Git optimization

- Cache the resolved Git common and administrative directories per workspace and
  invalidate on root identity change.
- Observe `HEAD` at each boundary where Git revision matters.
- Do not run three Git metadata subprocesses per capture.
- Do not compute Git blob hashes for every file on every call. Compute them only for
  changed candidates or when a consumer explicitly requires them.

## 5. M7 specification: production adapter and reproducible field quality

### 5.1 Sources of truth

The M7 pipeline has four deliberately separate artifacts:

| Artifact | Owner | Purpose | May contain expected label? |
| --- | --- | --- | --- |
| PatchMesh SQLite event log | PatchMesh runtime | Authoritative immutable facts | No |
| `.evidence/runtime` trace | Evidence recorder | Redacted run/lifecycle audit | No |
| Reviewed field label | Human reviewer | Expected detector outcome | Yes |
| Generated detector result | Phase 2 evaluator | Replayed observed outcome | No |

Neither a hook trace nor a reviewed label may replace the PatchMesh event log.

### 5.2 Production host adapter contract

Implement exactly one first production host adapter. The recommended first target is
the runtime actually used for PatchMesh agent/subagent work, but it is eligible only if
it provides synchronous around-tool interception. If Codex/OpenCode/another runtime
offers only a post-tool hook, that hook may feed lifecycle evidence but MUST NOT be
presented as the production executor-owning adapter.

Runtime-specific code belongs under `packages/adapters`; lifecycle composition belongs
in the daemon or the selected host entrypoint. The core MUST remain runtime-agnostic.

The adapter MUST expose a capability declaration:

```ts
interface HostAdapterCapabilities {
  readonly schemaVersion: 1;
  readonly runtime: string;
  readonly runtimeVersion: string;
  readonly adapterVersion: string;
  readonly wrapsToolExecution: true;
  readonly authoritativeIdentity: boolean;
  readonly taskLifecycle: boolean;
  readonly exactReportedEffects: boolean;
  readonly integrationTargetSnapshot: boolean;
  readonly concurrentWorktreeObservation: boolean;
  readonly observedReadVersion: boolean;
  readonly dependentWriteToken: boolean;
}
```

The canonical tool path is:

```ts
const result = await proxy.execute(call, context, executor, signal);
const evidence = await readPersistedToolEvidence(store, result.completedEventId);
void evidenceRecorder.record(toEvidencePayload(runtimeContext, result, evidence));
return unwrapExecution(result.execution);
```

Required behavior:

1. Build `McpCallContext` from authoritative runtime/session configuration. Hook or
   tool payload identity may confirm this context but may not override it.
2. Persist `tool.requested` before invoking the executor.
3. Invoke the underlying executor exactly once.
4. Preserve success, failure, interruption, exit code, and abort behavior.
5. Await `McpProxy.execute` before reading persisted evidence.
6. Read the request, completion, and only completion-linked effect events from the same
   event store.
7. Pass the exact `McpProxyResult` plus persisted events to the evidence bridge.
8. Return the underlying tool result even if the recorder fails; expose a bounded,
   redacted recorder diagnostic separately.
9. Never infer effects from requested paths, command text, tool input/output, or model
   statements.
10. Record adapter/runtime version and a canonical capability digest with each field
    case export.

### 5.3 Identity and lifecycle rules

- `repositoryId` comes from PatchMesh metadata under the Git common directory.
- `worktreeId` comes from PatchMesh metadata under the worktree administrative
  directory.
- `workspaceId` identifies the current filesystem/execution context.
- `agentId`, `taskId`, and parent/child run relationships come from authoritative host
  lifecycle context.
- `integrationTarget` MUST resolve to an immutable target snapshot, not only a moving
  branch name.
- Adapter-generated source sequences are monotonic per source instance.
- A child run MUST reference an existing parent run and matching parent subagent-start
  record.
- Request and completion MUST share tool-call identity, attribution, correlation, and
  causation.
- One host tool call MUST map to one request and one terminal completion.

Missing identity or lifecycle proof degrades the affected capability. It MUST NOT be
filled with a guess.

### 5.4 Required relationship proofs

#### Same-symbol concurrency

The adapter/gateway may emit `task.concurrency.observed` only when it directly knows:

- two distinct tasks and agents;
- two distinct worktrees in the same repository;
- the same immutable integration target;
- overlapping observed task lifetimes or overlapping executor-owned tool windows;
- the two referenced persisted `symbol.changed` events;
- sufficient coverage for the concurrency observation.

Sequential tasks, shared timestamps, simultaneous process existence without task
identity, event ordering, or independent event roots are not concurrency proof.

#### Stale-read comparison

The adapter may emit a stale-comparison-bearing `write.dependent` only when:

- a prior read returned a durable observed-read token;
- the token binds repository, workspace/worktree, task, resource, observed version,
  read event ID, and integration target;
- the dependent write explicitly presents that token or an equivalent structured host
  relationship;
- the compared changed event is persisted and has sufficient coverage;
- the write effect is persisted and linked to the same tool completion.

A generic later edit in the same task is not proof that the edit depended on the read.
If the runtime cannot carry a read/dependency token, stale-read capability remains
degraded and cannot contribute M7 stale-detector cases.

#### Exported-contract invalidation

The field case MUST include hash-bound source analysis, exactly one sufficient derived
evidence record per target, a resolver-confirmed consumer dependency, matching
integration target, and the candidate contract change. Ambiguous analyzer evidence or
cross-target consumers fail closed.

### 5.5 Field artifact layout

Use this separation:

```text
.evidence/
  config.json                         # committed
  schema/                             # committed schemas
  fixtures/                           # committed synthetic tests
  runtime/                            # ignored raw local traces/manifests
  corpus/
    field-v2/
      inputs/<case-id>.json           # reviewed minimized protocol-event slice
      labels/<case-id>.json           # reviewer label, separate from output
      corpus.json                     # case index
  field-output/                       # ignored generated per-case output
  reports/                            # generated; commit only accepted reviewed report
```

Existing `.evidence/trace` files may remain historical attribution fixtures, but MUST
NOT be relabeled as M7 detector-quality cases.

Every promoted real field input MUST be:

- exported from the SQLite event log by a deterministic exporter;
- minimized to the transitive causal/reference closure required by the target case;
- validated by the protocol/replay validator;
- canonicalized and SHA-256 bound;
- redaction-scanned and path-confined;
- reviewed before commit;
- free of prompts, hidden reasoning, secrets, full environment maps, and raw tool
  output.

### 5.7 Deterministic replay evaluator

Add a pure dispatcher:

```ts
function runFieldDetector(
  detector: FieldDetector,
  events: readonly ProtocolEvent[],
  target: FieldTarget,
): GeneratedDetectorResult
```

Its implementation MUST:

1. validate exact input schema and path confinement;
2. validate every protocol event and the complete reference set;
3. replay the event set; invalid replay returns `unavailable`, not a negative;
4. call the public core derivation and detector functions:
   - `deriveSameSymbolEvidence` + `runSameSymbolDetector`;
   - `deriveStaleReadEvidence` + `runStaleReadBeforeWriteDetector`;
   - `deriveExportedContractInvalidationEvidence` +
     `runExportedContractInvalidationDetector`;
5. match findings to the declared target resource/task;
6. set `observedFinding` from matching generated findings;
7. set `predictedProbability` to the maximum matching finding confidence, or `0` when
   there is no matching finding;
8. write canonical output and recompute its digest;
9. load the reviewer label only after detector execution;
10. compute metrics from generated output versus reviewer label.

No corpus field may override generated `observedFinding`, probability, finding ID,
detector version, or output digest.

Evaluation MUST be deterministic under canonical, duplicate, and every valid
out-of-order input variant. Invalid variants are diagnostics, not negatives.

### 5.8 Holdout design and quality thresholds

The current 20-case structural threshold may remain as a pilot/collection milestone,
but it MUST NOT accept the Phase 2 M7 exit gate.

For each detector, the exit-gate holdout MUST contain at least:

- 30 independently reviewed positive cases;
- 150 independently reviewed negative cases;
- multiple repositories or materially distinct scenario families;
- no duplicate protocol-event-set digest;
- no train/holdout pair produced by trivial renaming of the same fixture;
- only sufficient-coverage cases for quality scoring.

Degraded and unavailable real cases MUST be retained in a separate coverage report,
but MUST NOT be scored as true negatives.

Thresholds per detector:

- precision >= 0.95;
- recall >= 0.90;
- Brier score <= 0.10, using the reviewed expected label and generated probability;
- observed false-positive rate <= 0.02;
- one-sided 95% Wilson upper bound for false-positive rate <= 0.02.

The Wilson requirement makes the 2% false-positive claim evidence-backed. With zero
false positives, roughly 150 independent negatives are needed to put the one-sided
95% upper bound below 2%.

Thresholds, minimum counts, confidence method, and detector list MUST live in one
versioned `benchmarks/phase2/m7-quality-gate.v1.json`. The evaluator and documentation
must read this file rather than duplicating constants.

### 5.9 Required real scenario matrix

Each row below requires at least one reviewed real-adapter case before large-scale
holdout collection.

| Detector | Positive cases | Required negative/degraded cases |
| --- | --- | --- |
| Same-symbol overlap | distinct agents/tasks/worktrees, same symbol/target, proven overlap | sequential tasks; same agent; same worktree; different target; different symbol; missing lifecycle; conflicting concurrency assertions |
| Stale read before write | durable read token for v1, sufficiently observed candidate v2, token-bound dependent write | current comparison; unrelated changed resource; missing token; cross-target; cross-task token; degraded coverage; write not completion-linked |
| Exported-contract invalidation | exported breaking change plus resolver-confirmed real consumer on same target | parameter rename; non-exported symbol; unrelated consumer; compatible signature; different target; ambiguous derived evidence; insufficient analyzer coverage |

The scenario harness MUST use temporary repositories and real linked worktrees. It may
coordinate agents, but it MUST NOT synthesize PatchMesh effects or insert detector
events by hand.

### 5.11 M7 security and retention

- `.evidence/runtime/**`, `.evidence/field-output/**`, locks, state, and unreviewed
  exports MUST be ignored.
- Runtime trace files SHOULD use owner-only permissions where supported.
- Apply maximum event count, bytes per event, trace bytes, run duration, and retention
  limits.
- Validate `additionalProperties: false` with the checked-in schemas, then perform
  semantic cross-event validation.
- Redact before writing; do not rely only on an export-time cleanup.
- Hashes provide integrity only when anchored by a trusted reviewed manifest. They do
  not provide authenticity.
- Signing/authentication remains a documented residual risk unless separately scoped.

### 5.12 M7 definition of done

M7 is accepted only when:

1. one named production host adapter wraps actual agent tool execution;
2. real parent and subagent runs produce authoritative identity/lifecycle evidence;
3. at least one real completion contains non-empty, deterministically attributed,
   completion-linked verified file effects;
4. the adapter emits real sufficient concurrency and stale-comparison proofs for the
   supported capabilities;
5. field inputs are deterministic exports from SQLite protocol events;
6. reviewer labels are separate from generated output;
7. the evaluator reruns detector code and derives observed outcome/confidence;
8. invalid or degraded input is reported separately and never scored as a negative;
9. per-detector holdout counts and thresholds in the versioned gate pass;
10. canonical, duplicate, and valid out-of-order variants produce equivalent findings;
11. raw evidence retention/redaction rules are enforced;
12. all standard checks pass from a clean checkout;
13. docs continue to state Phase 2 is partial/report-only until every Phase 2 exit gate
    is separately closed.
